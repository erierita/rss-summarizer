## 4. Lambda関数仕様

### 4.1 FetchFeedFunction

#### 4.1.1 概要

| 項目 | 内容 |
|---|---|
| 機能 | RSSフィードを取得し、記事情報をSQSへ投入する |
| 起動契機 | EventBridge（DailyRule） |
| ファイル | lambda/fetch_feed/index.py |

#### 4.1.2 入力

EventBridgeのスケジュールイベント。**内容は使用しない**。

#### 4.1.3 環境変数

| 変数名 | 型 | 必須 | 内容 |
|---|---|---|---|
| QUEUE_URL | String | ○ | 投入先SQSのURL |
| FEED_URLS | String | ○ | 対象フィードURL（カンマ区切り） |
| MAX_ARTICLES | String | - | 1フィードあたり最大件数。既定 "3" |

#### 4.1.4 処理手順

| # | 処理 |
|---|---|
| 1 | 受信イベントをINFOログに出力する |
| 2 | FEED_URLSをカンマで分割し、空要素を除いてループする |
| 3 | フィードURLへHTTP GETを実行する（タイムアウト20秒、User-Agent設定） |
| 4 | 取得したXMLをパースする（4.1.5参照） |
| 5 | 記事リストを先頭MAX_ARTICLES件に絞る |
| 6 | 記事ごとにurl_hashを算出する（SHA-256の先頭32文字） |
| 7 | メッセージを構築しSQSへ送信する |
| 8 | 送信件数をカウントする |
| 9 | 全フィード処理後、送信件数を返却する |

#### 4.1.5 RSSパース仕様

RSS 2.0とAtom 1.0の両方に対応する。

| 形式 | 判定方法 | title取得元 | url取得元 |
|---|---|---|---|
| RSS 2.0 | `item` 要素が存在する | `item/title` | `item/link` のテキスト |
| Atom 1.0 | `item` が0件の場合に試行 | `atom:entry/atom:title` | `atom:entry/atom:link` の href属性 |

Atomの名前空間は `http://www.w3.org/2005/Atom` とする。

titleまたはurlが空の要素は除外する。

#### 4.1.6 出力

```json
{"sent": 3}
```

| 項目 | 型 | 内容 |
|---|---|---|
| sent | Number | SQSへ送信した件数 |

#### 4.1.7 例外処理

| 発生箇所 | 処理 |
|---|---|
| フィード単位のループ内 | try-except で捕捉し、`logger.exception` でログ出力後、次のフィードへ継続する |

**全フィードが失敗しても関数自体は正常終了**し、`{"sent": 0}` を返す。

#### 4.1.8 SQSメッセージ仕様

| 項目 | 値 |
|---|---|
| MessageBody | 記事情報のJSON文字列（ensure_ascii=False） |
| MessageAttributes | 使用しない |
| DelaySeconds | 使用しない |

### 4.2 EnqueueWorkerFunction

#### 4.2.1 概要

| 項目 | 内容 |
|---|---|
| 機能 | SQSメッセージを受信し、重複を除いてStep Functionsを起動する |
| 起動契機 | SQSイベントソース（ArticleQueue） |
| ファイル | lambda/enqueue_worker/index.py |

#### 4.2.2 入力

SQSイベント。最大5件のレコードを含む。

```json
{
  "Records": [
    {
      "messageId": "059f36b4-87a3-44ab-83d2-661975830a7d",
      "receiptHandle": "AQEBwJnKyrHigUMZj6rYigCgxlaS3SLy0a...",
      "body": "{\"url\":\"https://...\",\"title\":\"...\",\"url_hash\":\"...\"}",
      "attributes": {
        "ApproximateReceiveCount": "1",
        "SentTimestamp": "1545082649183"
      },
      "eventSource": "aws:sqs"
    }
  ]
}
```

#### 4.2.3 環境変数

| 変数名 | 型 | 必須 | 内容 |
|---|---|---|---|
| STATE_MACHINE_ARN | String | ○ | 起動対象のステートマシンARN |
| TABLE_NAME | String | ○ | 重複確認に使用するDynamoDBテーブル名 |

#### 4.2.4 処理手順

| # | 処理 |
|---|---|
| 1 | 受信レコード件数をINFOログに出力する |
| 2 | 失敗メッセージID格納用のリストを初期化する |
| 3 | Recordsをループする |
| 4 | `body` をJSONとしてパースする |
| 5 | url_hashでDynamoDBのGetItemを実行する |
| 6 | 該当アイテムが存在する場合、ログ出力して次のレコードへ（スキップ） |
| 7 | Step Functionsを起動する（実行名は4.2.5参照） |
| 8 | 起動成功をログに出力する |
| 9 | 全レコード処理後、失敗メッセージIDのリストを返却する |

#### 4.2.5 Step Functions 実行名の採番

```
exec-{url_hash}-{UNIX秒}
```

**設計意図**

Step Functionsは同名の実行を作成できない。url_hashのみでは同一記事の再実行が不可能になるため、UNIX秒を付与して一意性を確保する。

重複処理の防止は、DynamoDBの存在確認（手順5-6）が担う。

#### 4.2.6 出力

```json
{
  "batchItemFailures": [
    {"itemIdentifier": "059f36b4-87a3-44ab-83d2-661975830a7d"}
  ]
}
```

| 項目 | 型 | 内容 |
|---|---|---|
| batchItemFailures | Array | 処理に失敗したメッセージIDのリスト |

**この形式で返却することにより、失敗したメッセージのみがキューに戻る。** 成功したメッセージは削除され、再処理されない。

#### 4.2.7 例外処理

| 例外 | 処理 |
|---|---|
| ExecutionAlreadyExists | 既に起動済みとみなし、成功扱いとする（batchItemFailuresに追加しない） |
| DynamoDB参照失敗（ClientError） | ログ出力後、未処理とみなして処理を継続する |
| その他の例外 | ログ出力後、batchItemFailuresに追加する |

#### 4.2.8 重複確認処理

```
関数名: already_processed(url_hash) -> bool

処理:
  1. DynamoDBのGetItemをKey={"url_hash": url_hash}で実行
  2. レスポンスに "Item" が含まれればTrueを返す
  3. ClientError発生時はログ出力しFalseを返す（処理を継続させる）
```

### 4.3 FetchArticleFunction

#### 4.3.1 概要

| 項目 | 内容 |
|---|---|
| 機能 | 記事本文を取得し、テキスト抽出後にS3へ保存する |
| 起動契機 | Step Functions（本文取得ステート） |
| ファイル | lambda/fetch_article/index.py |

#### 4.3.2 入力

Step Functionsの実行入力がそのまま渡される。

| 項目 | 型 | 必須 | 内容 |
|---|---|---|---|
| url | String | ○ | 記事URL |
| title | String | ○ | 記事タイトル |
| url_hash | String | ○ | URLのハッシュ値 |
| feed_url | String | - | 取得元フィードURL |

#### 4.3.3 環境変数

| 変数名 | 型 | 必須 | 内容 |
|---|---|---|---|
| BUCKET_NAME | String | ○ | 保存先S3バケット名 |

#### 4.3.4 処理手順

| # | 処理 |
|---|---|
| 1 | 入力をINFOログに出力する |
| 2 | urlへHTTP GETを実行する（タイムアウト30秒、User-Agent設定） |
| 3 | レスポンスヘッダから文字コードを判定する（取得不可の場合はutf-8） |
| 4 | 判定した文字コードでデコードする（errors="replace"） |
| 5 | HTMLからテキストを抽出する（4.3.5参照） |
| 6 | S3キーを `articles/{url_hash}.txt` として構築する |
| 7 | S3へPutObjectを実行する |
| 8 | 保存結果をINFOログに出力する |
| 9 | 入力をマージした出力を返却する |

#### 4.3.5 テキスト抽出仕様

`html.parser.HTMLParser` を継承したクラスで実装する。

| 処理 | 内容 |
|---|---|
| 除外タグ | script, style, noscript の開始タグから終了タグまでの内容を無視する |
| テキスト収集 | 上記以外のテキストノードを前後空白除去して収集する |
| 空文字の除外 | 空白のみのテキストは収集しない |
| 正規化 | 収集したテキストを半角スペースで連結後、連続する空白文字を1つに置換する |

#### 4.3.6 出力

```json
{
  "url": "https://...",
  "title": "...",
  "url_hash": "f340f061...",
  "feed_url": "https://...",
  "s3_key": "articles/f340f061....txt",
  "body_length": 5432,
  "ttl": 1791536911
}
```

| 項目 | 型 | 内容 |
|---|---|---|
| （入力の全項目） | - | 入力をそのまま引き継ぐ |
| s3_key | String | 保存先のS3オブジェクトキー |
| body_length | Number | 抽出したテキストの文字数 |
| ttl | Number | 現在時刻 + 30日のUNIX秒 |

**入力をマージして返却する理由**

後続ステート（要約、DynamoDB保存、通知）がtitleやurlを必要とするため。返却値のみを返すと、これらの情報が失われる。

#### 4.3.7 例外処理

例外を捕捉しない。発生した例外はStep Functions側のRetry/Catchで処理する。

#### 4.3.8 S3 PutObject 仕様

| 項目 | 値 |
|---|---|
| Bucket | 環境変数 BUCKET_NAME |
| Key | articles/{url_hash}.txt |
| Body | 抽出テキストのUTF-8バイト列 |
| ContentType | text/plain; charset=utf-8 |

### 4.4 SummarizeFunction

#### 4.4.1 概要

| 項目 | 内容 |
|---|---|
| 機能 | S3から本文を取得し、Bedrockで要約を生成する |
| 起動契機 | Step Functions（要約ステート） |
| ファイル | lambda/summarize/index.py |

#### 4.4.2 入力

FetchArticleFunctionの出力がそのまま渡される。

| 項目 | 型 | 必須 | 使用 |
|---|---|---|---|
| s3_key | String | ○ | ○ |
| title | String | ○ | ○ |
| （その他の項目） | - | - | 出力にマージするため保持 |

#### 4.4.3 環境変数

| 変数名 | 型 | 必須 | 内容 |
|---|---|---|---|
| BUCKET_NAME | String | ○ | 本文取得元のS3バケット名 |
| BEDROCK_MODEL_ID | String | ○ | 使用するモデルID |

#### 4.4.4 処理手順

| # | 処理 |
|---|---|
| 1 | 入力のキー一覧をINFOログに出力する |
| 2 | S3からs3_keyのオブジェクトを取得する |
| 3 | UTF-8でデコードし、先頭8,000文字に切り詰める |
| 4 | プロンプトを構築する（4.4.5参照） |
| 5 | Bedrock Converse APIを呼び出す |
| 6 | レスポンスから要約テキストを抽出し、前後空白を除去する |
| 7 | トークン使用量をINFOログに出力する |
| 8 | 入力をマージした出力を返却する |

#### 4.4.5 プロンプト仕様

```
以下の技術記事を、日本語で3行に要約してください。

制約:
- 各行は箇条書き（・で開始）
- 専門用語はそのまま残す
- 要約以外の前置きや後書きは書かない

タイトル: {title}

本文:
{body}
```

| プレースホルダ | 埋め込む値 |
|---|---|
| {title} | 入力のtitle |
| {body} | S3から取得した本文（先頭8,000文字） |

#### 4.4.6 Bedrock呼び出しパラメータ

| パラメータ | 値 | 設定根拠 |
|---|---|---|
| modelId | 環境変数 BEDROCK_MODEL_ID | |
| messages | `[{"role": "user", "content": [{"text": prompt}]}]` | |
| inferenceConfig.maxTokens | 500 | 3行の要約に十分な長さ |
| inferenceConfig.temperature | 0.3 | 要約タスクは決定性を優先する |

#### 4.4.7 レスポンス解析

```
res["output"]["message"]["content"][0]["text"]
```

上記パスから要約テキストを取得し、`.strip()` で前後空白を除去する。

トークン使用量は `res["usage"]["inputTokens"]` および `res["usage"]["outputTokens"]` から取得する。

#### 4.4.8 出力

```json
{
  "url": "https://...",
  "title": "...",
  "url_hash": "...",
  "s3_key": "...",
  "body_length": 5432,
  "ttl": 1791536911,
  "summary": "・要約1行目\n\n・要約2行目\n\n・要約3行目"
}
```

| 項目 | 型 | 内容 |
|---|---|---|
| （入力の全項目） | - | 入力をそのまま引き継ぐ |
| summary | String | 生成された要約 |

#### 4.4.9 例外処理

例外を捕捉しない。Step Functions側のRetry/Catchで処理する。

#### 4.5.4 処理手順

| # | 処理 |
|---|---|
| 1 | 入力からtitle, url, summaryを取得する（titleの既定値は "(タイトルなし)"） |
| 2 | 通知メッセージを構築する（4.5.5参照） |
| 3 | SLACK_WEBHOOK_URLが空の場合、メッセージをINFOログに出力し `notified: false` で返却する |
| 4 | Webhook URLへHTTP POSTを実行する（タイムアウト10秒） |
| 5 | レスポンスステータスをINFOログに出力する |
| 6 | 入力をマージし `notified: true` を付与して返却する |

#### 4.5.5 メッセージ書式

```
*{title}*
{url}

{summary}
```

Slackのmrkdwn記法により、`*` で囲んだ部分が太字になる。

#### 4.5.6 リクエスト仕様

| 項目 | 値 |
|---|---|
| メソッド | POST |
| Content-Type | application/json |
| ボディ | `{"text": "<メッセージ>"}`（ensure_ascii=False, UTF-8エンコード） |
| タイムアウト | 10秒 |

#### 4.5.7 出力

| 項目 | 型 | 内容 |
|---|---|---|
| （入力の全項目） | - | 入力をそのまま引き継ぐ |
| notified | Boolean | 通知の実行有無 |

## 5. Step Functions ステート定義

### 5.1 ステート一覧

| # | ステート名 | 種別 | 次のステート |
|---|---|---|---|
| 1 | 本文取得 | Task（Lambda） | 本文長を判定 |
| 2 | 本文長を判定 | Choice | 要約 または スキップ |
| 3 | 要約 | Task（Lambda） | DynamoDBへ保存 |
| 4 | DynamoDBへ保存 | Task（SDK統合） | Slack通知 |
| 5 | Slack通知 | Task（Lambda） | （終了） |
| 6 | スキップ（本文が短い） | Succeed | - |
| 7 | 処理失敗 | Fail | - |

### 5.2 本文取得

| 項目 | 値 |
|---|---|
| 種別 | Task（LambdaInvoke） |
| 対象 | FetchArticleFunction |
| payload_response_only | true |
| retry_on_service_exceptions | true |
| ResultPath | 指定なし（結果で入力を置換） |

**Retry設定**

| 項目 | 値 |
|---|---|
| errors | States.TaskFailed |
| interval | 2秒 |
| max_attempts | 2 |
| backoff_rate | 2.0 |

実際の待機時間は 1回目=2秒、2回目=4秒 となる。

**Catch設定**

| 項目 | 値 |
|---|---|
| errors | States.ALL |
| 遷移先 | 処理失敗 |
| ResultPath | 指定なし ※ 5.8の改善事項を参照 |

### 5.3 本文長を判定

| 項目 | 値 |
|---|---|
| 種別 | Choice |

**分岐条件**

| 条件 | 遷移先 |
|---|---|
| `$.body_length >= 300` | 要約 |
| 上記以外（Default） | スキップ（本文が短い） |

条件式には `Condition.number_greater_than_equals` を使用する。

### 5.4 要約

| 項目 | 値 |
|---|---|
| 種別 | Task（LambdaInvoke） |
| 対象 | SummarizeFunction |
| payload_response_only | true |
| retry_on_service_exceptions | true |
| ResultPath | 指定なし |

**Retry設定**

| 項目 | 値 |
|---|---|
| errors | States.TaskFailed |
| interval | 5秒 |
| max_attempts | 2 |
| backoff_rate | 2.0 |

実際の待機時間は 1回目=5秒、2回目=10秒 となる。本文取得より長いのは、Bedrockのスロットリングからの回復に時間を要するため。

**Catch設定**

本文取得と同じ。

### 5.5 DynamoDBへ保存

| 項目 | 値 |
|---|---|
| 種別 | Task（DynamoPutItem。AWS SDK直接統合） |
| 対象テーブル | ArticleTable |
| **ResultPath** | **JsonPath.DISCARD** |

**格納項目**

| DynamoDB属性 | 型 | 値の取得元 |
|---|---|---|
| url_hash | S | `$.url_hash` |
| url | S | `$.url` |
| title | S | `$.title` |
| summary | S | `$.summary` |
| s3_key | S | `$.s3_key` |
| ttl | N | `States.JsonToString($.ttl)` |

ttlは数値型のため、`DynamoAttributeValue.number_from_string` に組み込み関数 `States.JsonToString` で文字列化した値を渡す。

**ResultPathにDISCARDを指定する理由**

DynamoPutItemの実行結果は `SdkHttpMetadata` 等のメタデータであり、業務上不要である。ResultPathを指定しない場合、この結果で入力が上書きされ、後続の通知ステートがtitleやsummaryを参照できなくなる。

DISCARDを指定することで結果を破棄し、入力をそのまま次のステートへ渡す。

**Lambdaを介さずSDK直接統合を用いる理由**

単純なPutItemのためだけにLambdaを作成・保守するコストを回避する。Step FunctionsはAWSサービスを直接呼び出せる。

### 5.6 Slack通知

| 項目 | 値 |
|---|---|
| 種別 | Task（LambdaInvoke） |
| 対象 | NotifyFunction |
| payload_response_only | true |
| Retry設定 | なし |
| Catch設定 | なし |

### 5.7 終端ステート

| ステート名 | 種別 | 内容 |
|---|---|---|
| スキップ（本文が短い） | Succeed | 正常終了として扱う |
| 処理失敗 | Fail | cause: "記事処理に失敗しました" |

### 5.8 改善事項

現行の実装には以下の課題がある。次版で対応する。

| ID | 課題 | 影響 | 対応方針 |
|---|---|---|---|
| SF-01 | Catchに ResultPath が未指定 | Failステートのcauseが固定文言となり、元の例外情報が失われる。障害調査時に `get-execution-history` を参照する必要がある | `add_catch` に `result_path="$.error"` を指定する |

**対応後の期待動作**

失敗時の入力に以下が付与される。

```json
{
  "url": "https://...",
  "error": {
    "Error": "ValidationException",
    "Cause": "{\"errorMessage\": \"...\"}"
  }
}
```

## 6. データ項目定義

### 6.1 url_hash

| 項目 | 内容 |
|---|---|
| 生成方法 | 記事URLをUTF-8エンコードし、SHA-256でハッシュ化した16進文字列の先頭32文字 |
| 実装 | `hashlib.sha256(url.encode()).hexdigest()[:32]` |
| 長さ | 32文字（固定） |
| 用途 | DynamoDBのパーティションキー、S3オブジェクトキー、Step Functions実行名の一部 |

**32文字に切り詰める理由**

SHA-256の完全な出力は64文字であるが、衝突確率を考慮しても32文字（128ビット相当）で十分である。キー長を抑えることでストレージ効率が向上する。

### 6.2 ttl

| 項目 | 内容 |
|---|---|
| 生成方法 | 処理時点のUNIX秒 + 30日（2,592,000秒） |
| 実装 | `int(time.time()) + 30 * 24 * 3600` |
| 生成箇所 | FetchArticleFunction |
| 用途 | DynamoDBのTTL属性 |

**FetchArticleFunctionで生成する理由**

処理の起点に近い箇所で採番することで、リトライ時も値が安定する。

### 6.3 s3_key

| 項目 | 内容 |
|---|---|
| 形式 | `articles/{url_hash}.txt` |
| 例 | `articles/f340f06190c76be66b5984281afe4b3e.txt` |

## 8. ログ出力仕様

## 付録A：実装上の留意点

| # | 項目 | 内容 |
|---|---|---|
| 1 | 論理IDの変更 | CDKの第2引数（論理ID）を変更すると、CloudFormationは別リソースと判断し再作成する。DynamoDBの論理ID変更はデータ消失を招く |
| 2 | 可視性タイムアウト | Lambdaのタイムアウトより必ず長く設定する。短いと処理中に別のLambdaが同一メッセージを取得する |
| 3 | ResultPath | Step FunctionsのTaskでは、結果が入力を上書きする既定動作を理解した上で設定する |
| 4 | 入力のマージ | Step Functionsから呼ばれるLambdaは `{**event, ...}` の形で入力を引き継ぐ |
| 5 | 冪等性 | SQS標準キューは重複配信の可能性がある。処理は冪等に実装する |
| 6 | 環境変数と機密情報 | 環境変数はCloudFormationテンプレートに平文で記録される。機密情報はSecrets Managerを使用する |
