## 1. システム概要

### 1.1 目的

技術情報の収集にかかる工数を削減する。

エンジニアが日々確認すべき技術ブログは増加傾向にあり、すべてに目を通す時間の確保が難しい。本システムは新着記事を自動収集し、生成AIによる要約を提供することで、担当者が「読むべき記事」を短時間で判断できるようにする。

### 1.2 システムの位置づけ

社内向けの情報収集支援ツール。基幹業務には該当せず、停止しても業務継続に影響しない。

### 1.3 利用者

| 利用者 | 役割 |
|---|---|
| 開発チームメンバー | Slack通知を受け取り、要約を読む |
| システム管理者 | 対象フィードの追加・削除、障害対応 |

## 2. 要件

### 2.1 業務要件

| ID | 要件 |
|---|---|
| BR-01 | 指定した技術ブログのRSSから新着記事を自動収集する |
| BR-02 | 各記事の本文を取得し、要点を3行程度に要約する |
| BR-03 | 要約結果をSlackへ通知する |
| BR-04 | 収集・要約した結果を一定期間保持し、後から参照できる |
| BR-05 | 同一記事を重複して処理・通知しない |

### 2.2 非機能要件

| 分類 | ID | 要件 |
|---|---|---|
| 性能 | NF-01 | 1日あたり最大50件の記事を処理できる |
| 性能 | NF-02 | 起動から全件処理完了まで30分以内 |
| 可用性 | NF-03 | 稼働率の保証なし。失敗時は翌日の実行で回復を許容 |
| 可用性 | NF-04 | 一部記事の処理失敗が他記事の処理を妨げない |
| 保守性 | NF-05 | 対象フィードの追加は設定変更とデプロイのみで対応できる |
| 保守性 | NF-06 | インフラ構成をコードで管理し、環境を再現できる |
| セキュリティ | NF-07 | 保存データを暗号化する |
| セキュリティ | NF-08 | 各コンポーネントに最小権限のみ付与する |
| セキュリティ | NF-09 | 外部から直接アクセス可能なエンドポイントを設けない |
| コスト | NF-10 | 月額 10 USD 以内 |
| 運用 | NF-11 | 処理失敗を検知できる |

### 2.3 スコープ外

以下は本システムの対象外とする。

- 記事の全文検索機能
- 過去記事の遡り収集
- 日本語以外の記事の要約
- Webブラウザからの参照UI
- 要約結果の編集・フィードバック機能
- マルチテナント対応

## 4. AWSサービス選定

選定理由と検討した代替案を記録する。

### 4.1 定期実行：EventBridge

| 項目 | 内容 |
|---|---|
| **選定** | Amazon EventBridge（スケジュールルール） |
| **理由** | サーバー管理が不要。cron式で柔軟に設定でき、実行頻度の変更がコード修正のみで完結する |
| **代替案1** | EC2上のcron → 常時起動のコストが発生し、要件NF-10に反する |
| **代替案2** | Lambda + 自己再帰呼び出し → 実装が複雑で障害時の挙動が読みにくい |

### 4.2 処理の順序制御：Step Functions

| 項目 | 内容 |
|---|---|
| **選定** | AWS Step Functions（標準ワークフロー） |
| **理由** | 分岐・リトライ・エラー処理を宣言的に定義でき、実行履歴から失敗箇所を特定しやすい。要件NF-11を満たす |
| **代替案1** | 単一Lambdaに全処理を実装 → どの工程で失敗したか追跡困難。タイムアウト15分の制約 |
| **代替案2** | Lambda間の直接呼び出し → エラー処理を各Lambdaに実装する必要があり保守性が低い |
| **補足** | Expressワークフローは実行履歴が残らないため、標準ワークフローを選択 |

### 4.3 記事の一時保持：SQS

| 項目 | 内容 |
|---|---|
| **選定** | Amazon SQS（標準キュー） |
| **理由** | 大量記事流入時のバッファとして機能し、Lambdaの同時実行数を制御できる。失敗時の再試行とDLQが標準機能 |
| **代替案1** | Lambdaから直接Step Functions起動 → 記事数が多いとスロットリングが発生 |
| **代替案2** | FIFOキュー → 記事の処理順序に意味がなく、スループット制約のデメリットが上回る |

### 4.4 本文の保存：S3

| 項目 | 内容 |
|---|---|
| **選定** | Amazon S3 |
| **理由** | DynamoDBは1アイテム400KBの上限があり、記事本文が超過する可能性がある。S3は容量無制限かつ保存コストが低い |
| **代替案** | DynamoDBに本文も格納 → サイズ超過リスク、読み書きコスト増 |

### 4.5 要約結果の保存：DynamoDB

| 項目 | 内容 |
|---|---|
| **選定** | Amazon DynamoDB（オンデマンドキャパシティ） |
| **理由** | URLハッシュによる単純なキー検索のみで、リレーショナルな操作が不要。オンデマンドで実行時のみ課金される |
| **代替案1** | RDS → 常時起動でコスト高。要件に対して過剰 |
| **代替案2** | S3のみ → 重複確認のための検索が非効率 |

### 4.6 要約生成：Bedrock

| 項目 | 内容 |
|---|---|
| **選定** | Amazon Bedrock（Claude Haiku 4.5、jp推論プロファイル） |
| **理由** | マネージドサービスでモデルの運用が不要。jp推論プロファイルによりデータが国外に出ない |
| **代替案1** | 自前でLLMをホスト → GPU費用と運用負荷が要件に見合わない |
| **代替案2** | 外部LLM API → 記事本文が社外へ送信される。データ所在地の制御ができない |
| **モデル選定** | 要約タスクには軽量モデルで十分。Haikuは応答速度とコストの両面で有利 |

### 4.7 通知：Slack Incoming Webhook

| 項目 | 内容 |
|---|---|
| **選定** | Slack Incoming Webhook |
| **理由** | 既存の業務コミュニケーション基盤。追加の認証基盤が不要 |
| **代替案** | Amazon SNS（メール） → 既読管理がしづらく、埋もれやすい |

## 5. 処理方式設計

### 5.1 処理タイミング

| 処理 | 契機 | 頻度 |
|---|---|---|
| RSS収集 | EventBridgeスケジュール | 1日1回（JST 09:00） |
| 記事処理 | SQSメッセージ受信 | 記事1件ごと |

### 5.2 処理フロー（正常系）

| # | 処理 | 実行主体 | 内容 |
|---|---|---|---|
| 1 | 起動 | EventBridge | FetchFeedFunctionを呼び出す |
| 2 | RSS取得 | FetchFeedFunction | 設定された各フィードURLへHTTPS GET |
| 3 | 記事抽出 | FetchFeedFunction | RSS2.0またはAtomをパースし、タイトルとURLを取得。上位N件に絞る |
| 4 | キュー投入 | FetchFeedFunction | 記事1件ごとにメッセージを生成しSQSへ送信 |
| 5 | メッセージ受信 | EnqueueWorkerFunction | SQSトリガーで最大5件をまとめて受信 |
| 6 | 重複確認 | EnqueueWorkerFunction | DynamoDBにurl_hashが存在するか確認。存在すればスキップ |
| 7 | ワークフロー起動 | EnqueueWorkerFunction | Step Functionsを記事1件ごとに起動 |
| 8 | 本文取得 | FetchArticleFunction | 記事URLへHTTPS GET、HTMLタグを除去 |
| 9 | 本文保存 | FetchArticleFunction | 抽出したテキストをS3へ保存 |
| 10 | 本文長判定 | Step Functions | 300文字未満ならスキップして正常終了 |
| 11 | 要約生成 | SummarizeFunction | S3から本文を取得しBedrockへ送信 |
| 12 | 結果保存 | Step Functions | DynamoDBへ直接PutItem |
| 13 | 通知 | NotifyFunction | Slackへ要約を送信 |

### 5.3 重複排除方式

同一記事の重複処理を2段階で防止する。

| 段階 | 方式 | 目的 |
|---|---|---|
| 1 | DynamoDBの存在確認 | 過去に処理済みの記事をスキップ |
| 2 | DynamoDBのPutItem（上書き） | 万一重複しても結果が同一になる（冪等性） |

url_hashは記事URLのSHA-256ハッシュ先頭32文字とする。

### 5.4 並行処理・多重度

| 項目 | 設定 | 理由 |
|---|---|---|
| SQSバッチサイズ | 5 | Lambda起動回数を抑制 |
| Lambda同時実行数 | 無制限（アカウント上限に従う） | 想定処理件数が少ない |
| Step Functions同時実行 | 記事ごとに1実行 | 記事間に依存関係がない |

## 6. データ設計

### 6.1 DynamoDB：ArticleTable

| 項目 | 内容 |
|---|---|
| テーブル論理名 | ArticleTable |
| パーティションキー | url_hash（String） |
| ソートキー | なし |
| キャパシティモード | オンデマンド（PAY_PER_REQUEST） |
| TTL属性 | ttl |
| 削除ポリシー | DESTROY（学習用。本番はRETAIN） |

**属性定義**

| 属性名 | 型 | 必須 | 内容 |
|---|---|---|---|
| url_hash | String | ○ | 記事URLのSHA-256先頭32文字。パーティションキー |
| url | String | ○ | 記事のURL |
| title | String | ○ | 記事タイトル |
| summary | String | ○ | 生成された要約（3行程度） |
| s3_key | String | ○ | 本文を保存したS3オブジェクトキー |
| ttl | Number | ○ | 削除予定時刻（UNIX秒）。登録から30日後 |

**アクセスパターン**

| # | 用途 | 操作 | キー |
|---|---|---|---|
| 1 | 重複確認 | GetItem | url_hash |
| 2 | 結果登録 | PutItem | url_hash |

### 6.2 S3：ArticleBucket

| 項目 | 内容 |
|---|---|
| オブジェクトキー | `articles/{url_hash}.txt` |
| コンテンツタイプ | text/plain; charset=utf-8 |
| 暗号化 | SSE-S3（S3管理キー） |
| パブリックアクセス | 全面ブロック |
| ライフサイクル | 30日で自動削除 |
| バージョニング | 無効 |

### 6.3 SQSメッセージ

**ArticleQueue のメッセージ本文（JSON）**

| 項目 | 型 | 内容 |
|---|---|---|
| url | String | 記事のURL |
| title | String | 記事タイトル |
| url_hash | String | URLのハッシュ値 |
| feed_url | String | 取得元フィードのURL |

```json
{
  "url": "https://aws.amazon.com/jp/blogs/news/iso-27001/",
  "title": "Kiro が ISO/IEC 27001:2022 のカバレッジに対応",
  "url_hash": "f340f06190c76be66b5984281afe4b3e",
  "feed_url": "https://aws.amazon.com/jp/blogs/news/feed/"
}
```

### 6.4 データ保持期間

| データ | 保持期間 | 削除方式 |
|---|---|---|
| DynamoDBの要約結果 | 30日 | TTLによる自動削除 |
| S3の記事本文 | 30日 | ライフサイクルルール |
| SQSメッセージ | 4日 | 保持期間経過で削除 |
| DLQメッセージ | 14日 | 保持期間経過で削除 |
| CloudWatch Logs | 7日 | 保持期間設定 |

## 7. 外部インターフェース設計

### 7.1 IF一覧

| IF-ID | 連携先 | 方向 | プロトコル | 契機 |
|---|---|---|---|---|
| IF-01 | 外部RSSフィード | 受信 | HTTPS (GET) | 定期実行時 |
| IF-02 | 外部Webサイト（記事本文） | 受信 | HTTPS (GET) | 記事処理時 |
| IF-03 | Amazon Bedrock | 双方向 | AWS SDK | 要約時 |
| IF-04 | Slack | 送信 | HTTPS (POST) | 通知時 |

### 7.2 IF-01：RSSフィード取得

| 項目 | 内容 |
|---|---|
| メソッド | GET |
| リクエストヘッダ | User-Agent を明示的に設定 |
| タイムアウト | 20秒 |
| 認証 | なし |
| 想定データ形式 | RSS 2.0 または Atom 1.0 |
| 取得項目 | title, link（Atomの場合は link の href属性） |
| 文字コード | XML宣言に従う |

**異常時の扱い**

| 事象 | 対応 |
|---|---|
| 接続失敗・タイムアウト | 当該フィードをスキップ。他フィードの処理は継続 |
| パース失敗 | 同上 |
| 記事0件 | 正常終了として扱う |

### 7.3 IF-02：記事本文取得

| 項目 | 内容 |
|---|---|
| メソッド | GET |
| リクエストヘッダ | User-Agent を明示的に設定 |
| タイムアウト | 30秒 |
| 認証 | なし |
| 文字コード | HTTPレスポンスヘッダの Content-Type から判定。取得できない場合はUTF-8 |
| 加工 | script / style / noscript タグの内容を除外し、テキストのみ抽出。連続空白を1つに正規化 |

**異常時の扱い**

| 事象 | 対応 |
|---|---|
| 接続失敗・タイムアウト | Step Functionsで2回リトライ後、当該記事を失敗扱い |
| デコード不能文字 | 置換文字で継続（例外としない） |

### 7.4 IF-03：Bedrock 要約

| 項目 | 内容 |
|---|---|
| API | Converse API（bedrock-runtime） |
| モデルID | jp.anthropic.claude-haiku-4-5-20251001-v1:0 |
| 認証 | IAMロール |
| 入力上限 | 本文の先頭8,000文字 |
| maxTokens | 500 |
| temperature | 0.3 |

**プロンプト**

```
以下の技術記事を、日本語で3行に要約してください。

制約:
- 各行は箇条書き（・で開始）
- 専門用語はそのまま残す
- 要約以外の前置きや後書きは書かない

タイトル: {title}

本文:
{body}
```

**異常時の扱い**

| 事象 | 対応 |
|---|---|
| スロットリング | Step Functionsで2回リトライ（5秒、10秒） |
| モデルID不正 | リトライせず失敗（設定誤りのため） |
| 権限不足 | 同上 |

### 7.5 IF-04：Slack通知

| 項目 | 内容 |
|---|---|
| メソッド | POST |
| URL | Incoming Webhook URL |
| Content-Type | application/json |
| タイムアウト | 10秒 |
| リクエストボディ | `{"text": "<メッセージ本文>"}` |
| 認証情報の管理 | Secrets Manager（`rss-summarizer/slack-webhook`）。Lambdaが実行時に取得しキャッシュする |

**メッセージ書式**

```
*{記事タイトル}*
{記事URL}

{要約}
```

**異常時の扱い**

| 事象 | 対応 |
|---|---|
| Webhook URL未設定 | 通知をスキップし、ログに出力。処理は成功扱い |
| 送信失敗 | 当該記事を失敗扱い（要約結果はDynamoDBに保存済み） |

## 8. エラー処理・例外設計

### 8.1 エラー処理方針

| 方針 | 内容 |
|---|---|
| 部分障害の許容 | 1件の記事処理失敗が他の記事に影響しない |
| 一時的障害への対応 | ネットワークエラー等はリトライで回復を図る |
| 恒久的障害の切り分け | リトライしても回復しないものはDLQへ退避し、調査可能な状態にする |
| 情報の保全 | エラー内容を握りつぶさず、原因追跡に必要な情報を残す |

### 8.2 リトライ設計

| 箇所 | 対象 | 回数 | 間隔 | バックオフ |
|---|---|---|---|---|
| Step Functions: 本文取得 | States.TaskFailed | 2 | 2秒 | 2.0倍 |
| Step Functions: 要約 | States.TaskFailed | 2 | 5秒 | 2.0倍 |
| SQS → Lambda | 全例外 | 3 | 可視性タイムアウト180秒後 | なし |

### 8.3 異常系一覧

| ID | 事象 | 検知箇所 | 対応 | 通知 |
|---|---|---|---|---|
| E-01 | RSSフィード取得失敗 | FetchFeedFunction | 当該フィードをスキップ | ログのみ |
| E-02 | 記事本文取得失敗 | Step Functions | 2回リトライ後Fail | DLQ経由で検知 |
| E-03 | 本文が300文字未満 | Step Functions Choice | 要約せず正常終了 | なし |
| E-04 | Bedrock呼び出し失敗 | Step Functions | 2回リトライ後Fail | DLQ経由で検知 |
| E-05 | DynamoDB書き込み失敗 | Step Functions | デフォルトリトライ後Fail | DLQ経由で検知 |
| E-06 | Slack通知失敗 | NotifyFunction | Fail | DLQ経由で検知 |
| E-07 | メッセージ処理失敗 | EnqueueWorkerFunction | 3回受信後DLQへ | DLQ滞留で検知 |

### 8.4 DLQ運用

| 項目 | 内容 |
|---|---|
| 移送条件 | ArticleQueueで3回受信されても削除されない場合 |
| 保持期間 | 14日 |
| 検知方法 | CloudWatch Alarm（ApproximateNumberOfMessagesVisible > 0） |
| 復旧手順 | 原因を修正後、SQSのリドライブ機能で元キューへ戻す |

## 10. 運用設計

### 10.1 監視

| 監視対象 | 方式 | しきい値 | 通知 |
|---|---|---|---|
| DLQのメッセージ滞留 | CloudWatch Alarm | ApproximateNumberOfMessagesVisible > 0 | 要設定 |

| Step Functionsの失敗 | CloudWatch Alarm | ExecutionsFailed > 0 | 要設定 |

※ 本設計時点ではアラーム未実装。今後の実装対象とする。

### 10.2 ログ

| 出力先 | 内容 | 保持期間 |
|---|---|---|
| CloudWatch Logs（Lambda毎） | 処理件数、エラー内容、スタックトレース | 7日 |
| Step Functions 実行履歴 | 各ステートの入出力、エラー | 90日（デフォルト） |

### 10.3 障害対応フロー

```
1. DLQのアラート受信、またはStep Functionsの失敗を確認
2. Step Functions 実行履歴で失敗したステートを特定
3. 該当LambdaのCloudWatch Logsでエラー内容を確認
4. 原因を修正しデプロイ
5. DLQからリドライブして再処理
```

### 10.4 設定変更手順

| 変更内容 | 手順 |
|---|---|
| 対象フィードの追加・削除 | `stacks/rss_summarizer_stack.py` の FEED_URLS を編集し `cdk deploy` |
| 実行時刻の変更 | 同ファイルの events.Schedule.cron を編集し `cdk deploy` |
| 取得件数の変更 | 同ファイルの MAX_ARTICLES を編集し `cdk deploy` |
| 一時停止 | events.Rule の enabled を False にし `cdk deploy` |

### 10.5 バックアップ

本システムのデータは再取得可能であり、消失しても業務影響がないため、バックアップは取得しない。

## 付録A：用語定義

| 用語 | 定義 |
|---|---|
| フィード | RSS/Atom形式で配信される記事一覧 |
| url_hash | 記事URLのSHA-256ハッシュ先頭32文字。記事の一意識別子 |
| DLQ | Dead Letter Queue。処理に失敗したメッセージの退避先 |
| 可視性タイムアウト | SQSで取り出したメッセージが他から見えなくなる時間 |
| 冪等性 | 同じ処理を複数回実行しても結果が変わらない性質 |
| 推論プロファイル | Bedrockで複数リージョンに負荷分散する呼び出し口 |
